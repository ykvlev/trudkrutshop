# Архитектура бэкенда ТрудКрутШоп

Краткий справочник по серверной части. Подробный контекст и обоснования — в
[plan.md](plan.md) (разделы 4–6).

## Стек

- **Next.js 16** (App Router, Turbopack), React 19, TypeScript — фронт и бэк в одном репозитории.
- **PostgreSQL** + **Prisma** — БД и типобезопасный доступ.
- Расширения Postgres: `pg_trgm`, `unaccent` (поиск с русской морфологией — включаются в `scripts/create-db.sql`).

## Слои и границы

```
src/
├── app/                     маршруты Next (витрина (shop), позже admin, api)
├── domain/                  бизнес-логика без привязки к фреймворку
│   ├── pricing.ts           расчёт цен/скидок/сертификатов (чистые функции)
│   └── stock.ts             движения склада, бронь, отгрузка
├── integrations/            внешние системы за интерфейсами (mock + реальный стаб)
│   ├── payment.ts           Точка: оплата, вебхуки
│   ├── fiscal.ts            Точка: фискальные чеки 54-ФЗ
│   ├── delivery.ts          SafeRoute: расчёт, ПВЗ, отправления
│   ├── edo.ts               ЭДО (Диадок/СБИС) для УПД, либо ручной PDF
│   ├── dadata.ts            реквизиты юрлица по ИНН
│   └── crm.ts               1С/Битрикс24 (заглушка на будущее)
└── lib/
    ├── prisma.ts            singleton-клиент Prisma
    ├── format.ts            форматирование цен, псевдослучайный порядок
    └── test-data.ts         тестовые данные витрины (до наполнения из БД)
```

**Принцип интеграций.** Каждая внешняя система прячется за интерфейсом
(`PaymentProvider`, `DeliveryProvider`, …). Фабрика `getXxxProvider()` выбирает
реализацию по наличию ключа в env: ключ есть → реальный провайдер, нет → mock.
Смена эквайринга/доставки или появление 1С меняет одну реализацию, а не половину кода.

## Модель данных (Prisma)

Полная схема — `prisma/schema.prisma`. Ключевые инварианты:

1. **Остатки и цены — на уровне варианта** (`ProductVariant`: размер × цвет × принт),
   а не товара. Требование ТЗ «наличие по каждому параметру».
2. **Остаток меняется только через `StockMovement`** (журнал движений с причиной).
   Прямая запись в `stock` запрещена — иначе не свести расхождения.
3. **Цена в заказе — снимок** (`OrderItem.priceSnapshot`): изменение прайса не
   меняет уже оформленные заказы.
4. **Бронь** (`ProductVariant.reserved`) между «оформил» и «оплатил»; доступно к
   покупке = `stock − reserved`.
5. **Документы и обмен** (`Invoice`, `Upd`, `IntegrationLog`) хранятся для юрлиц и
   разбора инцидентов.

## Команды

```bash
# Разовая подготовка БД (от суперпользователя Postgres):
psql -U postgres -p 5433 -f scripts/create-db.sql

npm run db:migrate     # применить/создать миграции (dev)
npm run db:seed        # засеять тестовыми данными
npm run db:studio      # Prisma Studio
npm test               # юнит-тесты (vitest)
```

## Переключение на реальную БД

Витрина и действия сейчас работают на тестовых данных и mock-провайдерах.
Слой готов к БД симметрично — чтение и запись:

| Слой | Сейчас | Файл-реализация под БД |
|---|---|---|
| Чтение витрины | `src/lib/data/test-data-source.ts` | `src/lib/data/prisma-repo.ts` |
| Запись/оформление | `src/lib/actions.ts` (mock) | `src/lib/actions-db.ts` |

Порядок активации:

```bash
npm install                 # на стабильной сети (движок Prisma)
npm run db:migrate          # применить схему к tksh_dev
npm run db:seed             # тестовый каталог
```

1. В `src/lib/data/index.ts` переключить источник на `./prisma-repo`.
2. В `src/lib/actions.ts` вызвать функции из `actions-db.ts` внутри
   соответствующих server actions (за флагом наличия БД).
3. Прописать боевые ключи интеграций в `.env` (тогда провайдеры выходят из mock).

Инварианты записи уже соблюдены в `actions-db.ts`: снимок цены в заказе,
изменение остатка только через журнал (`domain/stock.ts`), бронь между
«оформил» и «оплатил» и её снятие по таймауту.

## CI (GitHub Actions)

`.github/workflows/ci.yml` — на push и PR в main/master:

- **quality**: `npm install` → `prisma generate` → `prisma validate` → `next typegen`
  → `lint` → `typecheck` → `test` → `build`.
- **database**: поднимает Postgres 16 (service container), `prisma db push` на чистую
  БД и `db:seed` — проверяет, что схема и сид применяются без ошибок.

Локально в этом окружении установка пакетов не проходила (сеть), поэтому первый
прогон CI на GitHub — заодно первая полная проверка типов/линта слоёв БД и задач;
возможные замечания правятся по его логам.

## Тестирование (план §10)

- **Юнит** (vitest): расчёт цен/скидок/сертификатов, движения остатков — чистые функции.
- **Интеграционные**: заказ целиком на `tksh_test`, вебхуки, бронь при гонке.
- **E2E** (Playwright, позже): каталог → корзина → оформление → оплата в песочнице.
