# План разработки интернет-магазина «ТрудКрутШоп»

## Контекст

Есть ТЗ на интернет-магазин мерча РСО (футболки, худи, значки, аксессуары, подарочные сертификаты). Уже существует старый сайт на неизвестном движке — его надо заменить **на том же домене** с переносом данных и сохранением SEO. Рабочая папка `C:\Users\Артём\Documents\tksh` пуста — проект стартует с нуля.

Ключевая сложность ТЗ не в витрине, а в трёх контурах, которые обычно закрывают коробочные CMS:
1. **Товарная матрица** — остатки по каждой комбинации (размер × цвет × принт), а не по товару.
2. **Двойной сценарий продажи** — физлица (оплата картой + фискальный чек) и юрлица (ИНН → реквизиты → скидка → счёт → УПД через ЭДО).
3. **Складской контур** — списание при отгрузке, списание без оплаты (подарки/брак), влияние офлайн-продаж по кассе на онлайн-остатки.

**Решено:** Next.js + PostgreSQL, VPS в РФ, юрлица и УПД — сразу к запуску, чеки — через облачную кассу Точки, брендбук есть, макетов нет (собираем дизайн-систему под брендбук), дедлайн жёсткий.

**Результат:** работающий магазин с оплатой, доставкой, документооборотом для юрлиц и админкой, развёрнутый на своём VPS в РФ.

## Раздел 3. Что я рекомендую изменить в ТЗ

Перед стартом стоит согласовать с заказчиком четыре пункта. Каждый — либо невыполним, либо навредит проекту в текущей формулировке.

1. **Internet Explorer** → заменить на «актуальные версии Chrome, Firefox, Edge, Opera, Яндекс.Браузер, Safari + мобильные версии».
2. **«Каталог товаров выводится в случайном порядке» на главной** → случайный порядок на каждый запрос ломает кеширование и заставляет сервер работать вхолостую. Предлагаю: перемешивание с фиксированным зерном, которое меняется раз в несколько часов. Визуально — то же самое, для сервера — в разы дешевле.
3. **«Автоматическая загрузка по скроллингу И просмотр по страницам»** → чистый бесконечный скролл невидим для поисковиков. Делаем гибрид: кнопка «Показать ещё» с подгрузкой + настоящие URL-адреса страниц (`?page=2`) с `rel=next/prev`, доступные ботам. Формально удовлетворяет обоим требованиям.
4. **УПД** → в ТЗ это подано как функция сайта. По-хорошему это бухгалтерский документ: сайт формирует его и отправляет через ЭДО-оператора, но источником истины по нумерации и учёту должна быть учётная система. Если 1С появится — переносим туда.

| Слой | Выбор | Обоснование |
|---|---|---|
| Фронтенд + бэкенд | **Next.js 15** (App Router), React 19, TypeScript | Серверный рендеринг обязателен: ТЗ требует продвижения в Яндекс/Google. Один репозиторий вместо двух |

| Изображения | `next/image` + **sharp**, S3-совместимое хранилище (Timeweb S3 / Selectel) | Пункт ТЗ «медиаконтент автоматически перерабатывается в нужные размеры» закрывается ровно этим: WebP/AVIF, набор размеров, ленивая загрузка |
| Фоновые задачи | **pg-boss** (очередь поверх той же Postgres) | Отложенная отправка сертификатов, письма, синхронизации, ретраи вебхуков — без отдельного Redis |

| Поиск | Postgres `tsvector` + `pg_trgm` (русская морфология) | Для каталога такого размера отдельный поисковый движок избыточен |
| Админка | Собственная на Next.js + Auth.js | Требования ТЗ (списание брака, история заказов, сертификаты) слишком специфичны для готовой панели |
| Аналитика ошибок | Sentry (или self-hosted GlitchTip) | Обязательно для магазина с оплатой |
| Инфраструктура | Docker Compose, Caddy (авто-SSL), GitHub Actions | Простой предсказуемый деплой на один VPS |

### 4.3. Инфраструктура

**Сервер** (Timeweb Cloud / Selectel, обязательно ЦОД в РФ — 152-ФЗ требует хранить персональные данные россиян в России):
- Прод: 4 vCPU, 8 ГБ RAM, 80 ГБ NVMe
- Стейджинг: 2 vCPU, 4 ГБ RAM — отдельный сервер или контейнеры на том же с отдельным доменом

**Три окружения:** локальное → стейджинг (`stage.домен`, закрыт basic-auth, все интеграции в тестовом режиме) → прод.

**Бэкапы:** дамп Postgres каждые 6 часов + ежедневный в отдельное объектное хранилище, хранение 30 дней, **обязательная проверка восстановления** до запуска. Магазин с заказами и бухгалтерскими документами без проверенного бэкапа запускать нельзя.

## Раздел 5. Модель данных

Основные сущности Prisma. Полная схема — на 2-й неделе.

**Каталог**
- `Category` — id, slug, `parentId`, `path` (материализованный путь для быстрой выборки всего поддерева), name, description, `seoText` (тот самый текст над сеткой), image, sortOrder, isActive, seoTitle/seoDescription
- `Product` — id, slug, name, description, categoryId, basePrice, oldPrice, `isNew`, `isBestseller`, weight, длина/ширина/высота, sizeChartId, isActive, publishedAt, SEO-поля
- `ProductVariant` — id, productId, **sku**, size, color, print, price, oldPrice, **stock**, **reserved**, barcode. Ключевая таблица: остатки и цены живут здесь, потому что ТЗ требует наличие «по каждому параметру»
- `ProductImage` — productId, variantId (опционально — фото под конкретный цвет), url, alt, sortOrder
- `Attribute` / `AttributeValue` / `ProductAttribute` — произвольные характеристики для фильтров
- `SizeChart` — таблица размеров, привязывается к товару
- `ProductRelation` — productId, relatedId, type (`SIMILAR` | `BOUGHT_TOGETHER`), source (`MANUAL` | `AUTO`)

**Продажа**
- `Cart` / `CartItem` — гостевая корзина по cookie-токену, снимок цены на момент добавления
- `Order` — number, status, `customerType` (PHYSICAL | LEGAL), контакты, comment, тип и данные доставки, стоимость доставки, `trackNumber`, промокод, сумма скидки, subtotal, total, `paymentStatus`, paymentId, receiptId, legalEntityId, метки времени (создан / оплачен / отгружен / архивирован)
- `OrderItem` — снимок названия, цены, количества (цена в заказе не должна меняться, если потом поменяли прайс)
- `OrderStatusHistory` — from, to, кто, комментарий, когда → пункт ТЗ «сохранение истории обработки заказа»
- `LegalEntity` — ИНН, КПП, ОГРН, название, юр. адрес, банковские реквизиты, подписант
- `Invoice`, `Upd` — номер, дата, PDF, XML, статус в ЭДО

**Маркетинг**
- `PromoCode` — код, тип (процент/фикс), значение, минимальная сумма, лимит использований, срок действия, ограничение по категориям
- `Certificate` — code, дизайн, номинал, **остаток** (частичное погашение), email и телефон получателя, `sendAt` (отложенная отправка), sentAt, статус, заказ-источник и заказ-погашения
- `CertificateDesign`, `Banner` (десктоп/мобайл, ссылка, период показа)

**Склад**
- `StockMovement` — variantId, delta, `reason` (`ONLINE_SALE` | `OFFLINE_SALE` | `WRITE_OFF_GIFT` | `WRITE_OFF_DEFECT` | `RETURN` | `SYNC` | `MANUAL`), orderId, userId, комментарий, когда

Ни одно изменение остатка не пишется в `stock` напрямую — только через движение. Иначе через месяц никто не объяснит, куда делись пять худи.

**Служебное**
- `Page` (статические страницы), `RegionalPage` (секретный токен в URL), `AdminUser` + роли, `IntegrationLog` (весь обмен с Точкой/SafeRoute/ЭДО — для разбора инцидентов), `Redirect` (карта 301 со старого сайта)

## Раздел 6. Функциональные блоки

Соответствие пунктам ТЗ.

### 6.1. Витрина

**Главная.** Шапка (Каталог / Доставка / Оплата / О магазине / Контакты) + второй ряд (лого, Футболки, Худи, Значки, Аксессуары, Подарочные сертификаты, поиск, корзина со счётчиком) — сквозные, дублируются в подвале, там же иконки ВК и Telegram. Слайдер с навигацией внутри себя (стрелки + точки), каждый слайд ведёт на страницу акции. Ниже — сетка товаров в псевдослучайном порядке.

**Карточка товара в сетке.** Превью, название, цена, зачёркнутая старая цена, иконка корзины: с плюсом (не добавлен) → с галкой (добавлен), при наведении подсказка «Добавить товар в корзину» / «Товар добавлен в корзину». Изображение и название ведут в полную карточку. Добавление в корзину без перезагрузки страницы.

**Левая колонка.** Сквозная форма фильтров: категория, размер (интервалы), цена (интервал). Плюс маленькие баннеры со ссылками на ВК и сайт РСО. На мобильных превращается в выдвижную панель.

**Каталог.** Горизонтальное меню под шапкой, при наведении — выпадающий список разделов. Вложенность не ограничена, разделы правит администратор. Промежуточный раздел → страница-сетка подразделов с картинками. Конечный раздел → товары с сортировкой (Цена / Новинки / Размер, по умолчанию «Новинки», переключение ↑↓), SEO-текстом над сеткой и гибридной пагинацией.

**Карточка товара.** Фото напротив названия, галерея с зумом, крупная цена рядом с кнопкой «В корзину», выбор размера / цвета / принта (набор атрибутов настраивается — у значков размеров нет), кнопка «Таблица размеров» в модальном окне, **остаток по выбранной комбинации**, ниже карусели «Похожие товары» и «С этим покупают» до 20 позиций. Микроразметка Schema.org Product/Offer.

**Поиск.** По названию, описанию, SKU, с учётом русской морфологии и опечаток, подсказки при вводе.

### 6.2. Корзина и оформление

Открывается в текущем окне при клике на «В корзину» или иконку корзины. Таблица: превью, название со ссылкой на товар, цена, количество (по умолчанию 1, ограничено остатком), сумма, кнопка удаления. Внизу итоги — количество и сумма; те же цифры в анонсе корзины в шапке.

Далее по порядку: поле промокода или сертификата (пересчёт корзины на месте), поля «Имя», «Телефон», «E-mail», выбор способа доставки через SafeRoute или самовывоз, поле «Комментарий», кнопка «Оформить заказ как юридическое лицо», кнопка «Оформить заказ».

**Физлицо:** заказ → страница оплаты Точки → возврат на страницу статуса. Подтверждение приходит **только по вебхуку**, не по редиректу.

**Юрлицо:** обязательный ИНН → автоподтяжка реквизитов через DaData с возможностью правки → применение скидки → счёт на оплату (PDF) и УПД. Оплата по счёту, статус подтверждает менеджер в админке.

После оформления — письмо с составом заказа, а после создания отправления — письмо с трек-номером.

Отдельно: **резервирование остатка**. Между «оформил» и «оплатил» товар должен быть заблокирован (поле `reserved`), иначе двое купят последнюю футболку. Бронь снимается по таймауту, если оплаты нет.

### 6.3. Сертификаты

Выбор одного из дизайнов, произвольная сумма, e-mail и телефон получателя, время отправки (сразу после оплаты либо заданная дата и время) → в корзину как обычная позиция. После оплаты генерируется картинка сертификата с нанесённым кодом и уходит получателю в назначенное время (задача в очереди). Код применяется в корзине как средство оплаты; поддерживается частичное погашение с остатком на балансе.

Фискальный нюанс: продажа сертификата — аванс, а не реализация. Чеков будет два — при покупке и при погашении. Формулировку подтверждает бухгалтер (блокер №5).

### 6.4. Закрытая страница для регионов

Страница, доступная по ссылке с длинным непредсказуемым токеном, вне карты сайта, с `noindex`. Опционально — пароль. Содержимое правится в админке.

### 6.5. Админка

- **Заказы:** список с фильтрами и поиском, статусы («заказал физлицо» / «заказал, но не оплатил» / «оплачено физлицом» / «заказало юрлицо»), редактирование всех параметров (заказчик, товары, количество, цена, оплачен/не оплачен, доставлен/не доставлен, способ оплаты), полная история изменений, отмена и удаление, **создание заказа от имени клиента**, автоперенос выполненных в архив с сохранением счетов и УПД.
- **Товары:** карточки, фото, описания, размерные ряды и сетки, вес и габариты (нужны для расчёта доставки), варианты и остатки, массовый импорт из Excel.
- **Разделы:** дерево с перетаскиванием, SEO-поля, картинки.
- **Склад:** журнал движений, ручное списание с указанием причины (подарок, брак), приёмка, импорт офлайн-продаж.
- **Сертификаты:** список с признаком «использован / не использован», удаление, создание вручную.
- **Промокоды**, **баннеры**, **статические страницы**, **закрытые страницы регионалов**.
- **Пользователи админки** с ролями (администратор / менеджер / контент-менеджер).
- **Уведомление на e-mail администратора** о каждом новом заказе.

Правило: смена статуса на «отправлен» списывает товар со склада (`StockMovement`), а не наоборот.

### 6.6. Интеграции

| Система | Что делаем | Риск |
|---|---|---|
| **Точка Банк** | Создание платежа, страница оплаты, вебхук о статусе, фискальный чек через облачную кассу, возвраты | Документация закрыта до подписания договора — реальный объём работ виден только после доступа к ЛК. Заложен запас |
| **SafeRoute** | Расчёт стоимости по весу/габаритам/адресу, выбор ПВЗ на карте, создание отправления, трек-номер, вебхуки статусов | Требует корректных веса и габаритов у **каждого** товара — это к вам, в карточки |
| **ЭДО (Диадок/СБИС)** | Формирование УПД в формате ФНС (XML + PDF), подпись КЭП, отправка контрагенту, отслеживание статуса | Самый непредсказуемый блок. Если оператора нет — запасной вариант: PDF на подпись вручную |
| **DaData** | Реквизиты юрлица по ИНН, подсказки адресов | Низкий |
| **Пиксель ВК, Яндекс.Метрика** | Установка, цели, электронная коммерция | Низкий |
| **1С / Битрикс24** | Слой-заглушка с интерфейсом: выгрузка товаров, обмен остатками, передача заказов. Реальная реализация — когда появится система | Отложено |
| **Касса офлайн-магазина** | Импорт продаж, влияющих на остатки. Способ зависит от ответа на блокер №4 | Средний |

## Раздел 7. Нефункциональные требования

**Адаптивность.** Проектируем от мобильного. Контрольные ширины: 360, 768, 1024, 1440. Проверка на реальных устройствах, не только в эмуляторе браузера.

**Интерактив** (прямой пункт ТЗ). Явные состояния ссылок и кнопок (обычная, наведение, нажатая, посещённая, отключённая), хлебные крошки на всех страницах каталога, всплывающие подсказки, скелетоны при загрузке, понятные тексты ошибок.

**Производительность.** Цель Lighthouse ≥ 90 на мобильном для главной, каталога и карточки. Достигается за счёт серверных компонентов, WebP/AVIF, кеширования каталога, индексов под фильтры, шрифтов через `next/font`.

**SEO.** Уникальные `title`, `description`, `h1` на всех страницах; ЧПУ-адреса; микроразметка Product, Offer, BreadcrumbList, Organization; `sitemap.xml` и `robots.txt`; канонические адреса для страниц фильтров (иначе поисковик утонет в комбинациях); Open Graph; **карта 301-редиректов со старого сайта** — критично, иначе после переезда позиции обнулятся.

**Доступность.** Семантическая вёрстка, навигация с клавиатуры, alt у изображений, контраст по WCAG AA, `aria`-атрибуты у слайдера и модальных окон.

**Безопасность.** HTTPS, HSTS, CSP; ограничение частоты запросов на формах и в поиске; защита от подбора в админке; капча на формах; проверка подписи вебхуков; никаких карточных данных на нашей стороне (всё на стороне Точки); шифрование персональных данных в бэкапах; журнал действий администраторов.

**152-ФЗ.** Хранение и обработка в РФ, чекбокс согласия с активной ссылкой на политику, cookie-баннер, срок хранения данных, порядок удаления по запросу.

## Раздел 8. Календарный план

Дата дедлайна не названа (блокер №1), поэтому план в неделях от старта. Реалистичная оценка при полной занятости и своевременных ответах — **12 недель**. Треки идут параллельно там, где это возможно.

### Этап 0. Аудит и подготовка (неделя 1)
- Разбор старого сайта: движок, база, объём каталога, что можно выгрузить
- Сбор всех адресов старого сайта для карты редиректов
- Согласование правок ТЗ (раздел 3)
- Заказ VPS, домены, репозиторий, каркас Next.js + Postgres + Docker + CI
- Проектирование схемы БД
- Подача заявок на договоры: Точка, SafeRoute, ЭДО (**подавать в первую неделю** — согласование идёт неделями и это главный риск срыва срока)

### Этап 1. Фундамент (недели 2–3)
- Схема Prisma, миграции, сидирование тестовыми данными
- Дизайн-система на основе брендбука: цвета, типографика, кнопки, поля, карточки
- Каркас страниц: шапка, подвал, левая колонка, сетки
- Загрузка и обработка изображений, S3
- Каркас админки и авторизация
- **От вас:** брендбук, логотип, доступы к старому сайту, структура каталога

### Этап 2. Каталог (недели 3–5)
- Дерево разделов, страницы-сетки, конечные разделы
- Фильтры, сортировки, гибридная пагинация
- Карточка товара: галерея, варианты, остатки, таблица размеров, карусели связанных товаров
- Поиск с морфологией
- Главная: слайдер, блоки новинок, сниженных цен, лидеров продаж
- Импорт каталога из Excel + миграция со старого сайта
- **От вас:** товары, фото, размерные сетки, баннеры

### Этап 3. Корзина и оплата (недели 5–7)
- Корзина, резервирование остатков, промокоды
- Оформление для физлиц, интеграция с Точкой, фискальные чеки, вебхуки
- Интеграция с SafeRoute: расчёт, выбор ПВЗ, создание отправления, трек
- Транзакционные письма
- **От вас:** ключи Точки и SafeRoute, реквизиты, ставки НДС

### Этап 4. Юрлица и документы (недели 7–9)
- ИНН → DaData → реквизиты, скидка
- Генерация счёта (PDF)
- Генерация УПД (XML по формату ФНС + PDF), отправка через ЭДО
- Архив документов
- **От вас:** доступ к ЭДО, КЭП, условия скидки

### Этап 5. Сертификаты и склад (недели 8–10)
- Покупка сертификатов, генерация изображения с кодом, отложенная отправка
- Погашение, частичный остаток, управление в админке
- Журнал складских движений, списания без оплаты, импорт офлайн-продаж
- Слой-заглушка для 1С/Битрикс24
- **От вас:** дизайны сертификатов, ответ по офлайн-кассе

### Этап 6. Наполнение, SEO, отладка (недели 10–11)
- Заливка боевого каталога
- Мета-теги, микроразметка, sitemap, robots
- Карта 301-редиректов, подключение Метрики, пикселя ВК, Вебмастера, Search Console
- Юридические страницы, cookie-баннер, согласия
- Кроссбраузерное и мобильное тестирование, оптимизация скорости
- Сквозное тестирование на Playwright

### Этап 7. Запуск (неделя 12)
- Приёмочное тестирование по чек-листу ТЗ
- Тестовые боевые платежи и реальная отправка через SafeRoute
- Проверка восстановления из бэкапа
- Переключение домена, мониторинг, обучение менеджеров
- Наблюдение за первыми заказами в ручном режиме

### Критический путь

`Договоры с Точкой / SafeRoute / ЭДО` → `Этапы 3–4` → `Запуск`

Разработка витрины и каталога от этих договоров не зависит и идёт параллельно. Но если договоры затянутся, сдвинется всё. **Заявки нужно подать в первую неделю.**

### Если срок горит

Резать в таком порядке (сверху — наименее болезненное):
1. Импорт офлайн-продаж с кассы → ручное списание в админке
2. УПД через ЭДО → PDF на подпись вручную
3. Отложенная отправка сертификатов → отправка сразу после оплаты
4. Автоподбор «С этим покупают» → ручные связки в админке
5. Закрытая страница регионалов → простая страница с паролем

Не режется ни при каких условиях: оплата с фискальным чеком, доставка, корректные остатки, юридические страницы, бэкапы.

## Раздел 10. Проверка результата

**Автотесты**
- Модульные (Vitest): расчёт цен, скидок, промокодов, погашения сертификатов, движений остатков
- Интеграционные: заказ целиком на тестовой БД, вебхуки платежей, резервирование остатка при одновременной покупке
- Сквозные (Playwright): «каталог → фильтр → карточка → корзина → оформление физлицом → оплата в песочнице → письмо»; тот же путь для юрлица со счётом; покупка и погашение сертификата; работа админки
- CI гоняет всё на каждый push

**Ручная проверка перед запуском**
- Чек-лист по каждому пункту ТЗ (составлю отдельным документом на этапе 6) с отметкой «проверено» и скриншотом
- Браузеры: Chrome, Firefox, Edge, Opera, Яндекс.Браузер, Safari — десктоп и мобильные
- Устройства: iPhone, Android-смартфон, планшет, ноутбук, широкий монитор
- Реальный платёж на малую сумму через Точку + проверка чека в ОФД
- Реальное создание отправления в SafeRoute + проверка трека
- Отправка тестовой УПД контрагенту через ЭДО
- Письма: доставляемость, отсутствие в спаме, корректность в Gmail, Яндекс.Почте, Mail.ru, Outlook
- Lighthouse на главной, странице каталога и карточке товара
- Восстановление БД из бэкапа на стейджинге

**Как я буду показывать прогресс:** стенд на `stage.домен` обновляется на каждом этапе, вы смотрите вживую и даёте правки до того, как блок считается готовым.
